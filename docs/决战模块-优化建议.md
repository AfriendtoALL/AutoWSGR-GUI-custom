# AutoWSGR 决战模块（第六章）优化建议

> 范围：`ops/decisive/` 全部 + `ui/decisive/` 全部
> 前提：**不改动代码**，仅做审查与优化空间梳理，每条建议均附代码依据。
> 背景：决战第六章在代码里属于 `CombatMode.DECISIVE`（SINGLE 类、以 RESULT 为终止态）。宏观上由 `DecisiveController` 状态机驱动「章节 → 小关 → 节点」，微观上每一场战斗交给 `CombatEngine`。

---

## 一、第六章地图数据特征

决战地图是**静态硬编码**在 `ops/decisive/config.py` 的 `MapData` 里的（`_MAP_END` / `_KEY_POINTS`）。第六章与前面章节明显不同：

| 小关 | 终止节点 | 夜战关键点（需夜战） |
|------|----------|----------------------|
| 第 1 小关 | **J** | **B、G、J** |
| 第 2 小关 | **J** | **C、H、J** |
| 第 3 小关 | **J** | **D、G、J** |

- 对比前面的章节（如第 1~4 章有小关终止于 H），**第六章三段全部终止于 J，是节点链最长的一章**（每小关 A→B→…→J 共 10 个节点）。
- `is_stage_end()` 拿当前节点与 `map_end` 比较，打到 J 即小关结束；`is_key_point()` 决定该节点战斗结束时要不要进夜战。

---

## 二、核心决策逻辑速览（`DecisiveLogic` / 各 `_handle_*`）

- **战备舰队购买**（`choose_ships`）：舰队 ≤1 艘只买 Lv1；未满编买 Lv2 舰船；满编但混编则优先补齐 Lv1；全 Lv1 后才买增益技能。第一节点额外尝试买 Lv2 舰船。受 `score`（蜂蜜）预算约束。
- **撤退判定**（`should_retreat`）：节点 A 时舰船 <2 撤退，其他节点 <1 撤退；A 节点购买失败也会强制 RETREAT。
- **阵型选择**（`get_formation`）：读取 `MapData.get_enemy` 的敌方编成——反潜单位(CL/DD/CVL)≤0，或我方含 U-1206 且反潜≤1 → **梯形阵**；否则 **复纵阵**。
- **夜战**（`is_key_point`）：只有落在夜战关键点才进夜战（SINGLE 模式下 `default_node.night` 在 `_handle_combat` 里设好）。
- **技能利用**（`check_useful_skill`）：技能获取的船要满足「Lv1 占一半以上 / 单艘在 Lv2 列表」，否则判定「效果不佳」直接撤退重试（严格模式还会拒绝重复舰）。
- **修理**：`should_repair` 按 `repair_level` 决定；准备页修理策略 MODERATE/SEVERE 取决于 `repair_level<=1`。
- **分支前进**（`get_advance_choice`）：⚠️ **当前是 TODO，固定返回 0**——遇到分支点一律盲选第一个分支，没有按地图数据智能选路。

## 三、优化建议（按优先级）

### P0 · 功能缺口（影响第六章实跑）

**1. 分支前进是盲选 TODO**
- **依据**：`ops/decisive/logic.py:253-267` `get_advance_choice()` 直接 `return 0`，注释 `TODO: 根据地图数据和关键节点信息做出更智能的选择`。
- **影响**：第六章每小关都有 `ADVANCE_CHOICE` 分支点，目前一律选第一项，**无法保证走到夜战关键点（B/G/J 等）或避开难点**，直接削弱第六章作战策略。
- **建议**：把 `MapData` 已有的关键节点/终止节点数据接入 `get_advance_choice`，按「优先关键节点、避开死路」做选择。

**2. 节点递进靠字母硬加，无校验**
- **依据**：`ops/decisive/handlers.py:443-449` `expected_node = chr(ord(self._state.node) + 1)`。
- **影响**：隐式假设节点严格 A→B→…→J 连续。一旦分支导致跳节点，或 `recognize_node` 把节点识别偏（如 A↔B），后续阶段全错位且难察觉。
- **建议**：节点推进改为「基于 `MapData` 的当前小关节点序列查表取后继」，与 `is_stage_end` 共用同一数据源。

### P1 · 鲁棒性 / 脆弱特判

**3. 章节特调污染了通用识别函数**
- **依据**：`ui/decisive/map_controller.py:273` `get_ship_icon_pos()` 里写死 `# 针对Ex5特调，A节点不选择分支，直接进入战备舰队获取`，在通用节点识别里做了章节分支。
- **影响**：每加一个章节特性就要回头改这个通用函数，扩展性差、易回归。
- **建议**：把章节相关特判抽成可配置项（如 `config.py` 里按章节声明「首节点是否跳过分支」），识别函数保持纯粹。

**4. `recognize_node` 双层 retry + 嵌套超时**
- **依据**：`map_controller.py:282-356`，外层 `for retry in range(4)` 内又嵌 `get_ship_icon_pos_with_retry()`（内部 10s 轮询）。
- **影响**：最坏情况下单次节点识别耗时可达数十秒，且两层 retry 语义重叠、难以调参。
- **建议**：合并为单层带退避的轮询，用「稳定帧 + 置信度阈值」作为成功条件，超时统一抛错由上层恢复。

**5. 章节首进/恢复模式的修正逻辑散落且自嘲「一坨」**
- **依据**：`handlers.py:13` 注释 `# TODO 状态机建模一坨，之后再改`；`_handle_waiting_for_map`(160-181) 和 `_handle_prepare_combat`(277-281) 都有针对 Ex-1 首进的 overlay 误判修正；`handlers.py:455` `# TODO: 改进鲁棒性`。
- **影响**：这些修正都因 `detect_decisive_phase` 在过场/延迟加载时把「即将弹出的选船 overlay 首帧」误判为 `PREPARE_COMBAT`。补丁越打越多，脆弱。
- **建议**：让 `detect_decisive_phase` 自身做到「地图页需稳定两帧且无后续 overlay」再返回 `PREPARE_COMBAT`（其实现已部分做了 `map_controller.py:198-221`），把所有首进修正收敛到单一入口判定，handler 不再各自补丁。

**6. 敌人编成数据缺失被静默吞掉**
- **依据**：`config.py:120-140` `get_enemy` 节点缺失时返回 `[]`；`logic.py:276-285` 据此永远走 `wedge`（梯形阵）。
- **影响**：`enemy_spec.yaml` 若第六章某节点漏配，阵型会 silently 错配，且难以排查。
- **建议**：缺失时打 `warning`，并让 `get_formation` 在无法判断时回退到更保守的 `double_column`（复纵）。

### P2 · 可维护性 / 清理

**7. overlay 判定双轨并存（PixelSignature 已废弃未删）**
- **依据**：`overlay.py:59-129` 同时定义了 `SIG_*` 像素签名和 `_OVERLAY_TEMPLATE_MAP` 模板；`detect_decisive_overlay`(218-235) 只用模板，`get_overlay_signature`(265-267) 注释「保留备查, 不再参与判定」。
- **建议**：删除废弃的 `PixelSignature` 体系（`SKILL_USED` 那个 `map_controller.py:74-80` 仍在用，需一并迁移），只保留一套判定。

**8. 新旧换船算法双轨 + 开关**
- **依据**：`preparation.py:72-81` `use_new_fleet_change_algorithm` 决定走新算法或 `legacy_fleet_change.py` 整文件。
- **建议**：若新算法已在生产稳定，废止 `legacy_fleet_change.py`；若不稳定，应在日志/文档明确默认路径，避免两套逻辑长期并存增加回归面。

**9. `confirm_stage_clear` 一个方法 130 行、三套兜底循环**
- **依据**：`map_controller.py:814-943`，内含掉落等待、`while True` 收集掉落、12s settle、5 次返回按钮兜底。
- **建议**：拆分为 `collect_drops()` / `ack_reward_popups()` / `ensure_back_to_overview()` 三个小函数，各自可单测。

**10. 静态地图数据用字符串/列表硬编码、无校验**
- **依据**：`config.py:22-40` `_MAP_END=' JJJ'`（靠字符索引）、`_KEY_POINTS` 嵌套 list。
- **建议**：改用结构化 `dataclass`/`dict`，并在 `DecisiveConfig` 初始化时校验 1-6 章全部覆盖，防止漏写错位。

### P3 · 可读性 / 性能小事

- **裸 `time.sleep` 魔法数**：`handlers.py:309/354/375`（`sleep(0.5/0.5/1.0)`）、`map_controller.py:449`（`sleep(0.2)`）、`:905`（`sleep(0.3)`）应统一替换为 `wait_for_stable_screen` 或命名常量。
- **`choose_ships` 的 lim 计算绕**：`logic.py:116-117` 两步赋值等价于一个三目条件，建议化简便于审阅。
- **方法内延迟 `import Templates` 遍布**：`map_controller.py:170/459/687`、`battle_page.py:438` 等，是循环依赖的信号，建议通过顶层/注入理顺。
- **日志语义不符**：`handlers.py:299-305` 首节点判断里日志写「检测到恢复模式」，实际只是首节点分支，易误导排查。

---

## 四、总评

架构分层合理、主状态机清晰。最该优先处理的是 **P0-1（分支盲选）** 和 **P0-2（节点硬加）**——这两个直接决定第六章能不能按预期路线打；其余 P1 多为「补丁式修正 vs 根源修复」的工程债，建议借一次重构把 `detect_decisive_phase` 和入口判定收敛干净。

需要针对 P0 给出具体改造设计（仍不改代码、先给方案），可进一步展开。
